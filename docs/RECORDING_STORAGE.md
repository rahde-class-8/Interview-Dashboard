# Recording Storage

Status: **Proposed**
Scope: private upload, verification, playback, retention and deletion of call recordings
that users created with **other** applications.

Hard rules:

- The application **never records calls** and never requests microphone access.
- Audio binaries are **never stored in PostgreSQL** — only metadata and the object path.
- Recordings are **never publicly accessible**. No public bucket, no public URL, no
  long-lived links.

## 1. Storage layout

| Item | Value |
| --- | --- |
| Service | Supabase Storage |
| Bucket | `recordings`, `public = false` |
| Bucket file size limit | 100 MB (matches `NEXT_PUBLIC_MAX_RECORDING_SIZE_MB` default; raise both together) |
| Bucket allowed MIME types | `audio/mpeg`, `audio/mp4`, `audio/wav` |
| Object path | `{workspace_id}/{call_id}/{recording_id}.{ext}` — generated by the server; user file names are stored only as metadata |
| Storage RLS | **No policies** for `anon`/`authenticated` on `storage.objects` for this bucket. All reads/writes use server-issued signed URLs. |
| Metadata | `public.recording_attachments` (see DATABASE_SCHEMA §4.3) |

Accepted inputs and canonical MIME mapping (client-reported types are normalized):

| Extension | Accepted client MIME types | Canonical `mime_type` | Magic bytes checked |
| --- | --- | --- | --- |
| `.mp3` | `audio/mpeg`, `audio/mp3`, empty | `audio/mpeg` | `ID3` at 0, or MPEG frame sync `0xFFE` (11 bits) |
| `.m4a` | `audio/mp4`, `audio/x-m4a`, `audio/m4a`, `audio/aac`, empty | `audio/mp4` | `ftyp` at offset 4 with brand `M4A `, `mp42`, `isom` or `M4B ` |
| `.wav` | `audio/wav`, `audio/x-wav`, `audio/wave`, `audio/vnd.wave`, empty | `audio/wav` | `RIFF` at 0 and `WAVE` at 8 |

## 2. State machine

```
            init (API)                 complete (API, verified)
  (none) ──────────────▶ pending_upload ─────────────────────────▶ uploaded
                              │  verification fails                    │
                              ├────────────────────────▶ failed        │ user delete / retention /
                              │  not completed in 24 h       │          │ cascade
                              └────────────▶ (row deleted,   │          ▼
                                             object purged)  └──────▶ deleted ──▶ object purged,
                                                                                  row kept 30 days
                                                                                  as tombstone, then removed
```

Only `uploaded` recordings can be played. `failed` rows are shown with a retry option and
are cleaned up after 7 days.

## 3. Upload workflow

```
Browser                         Next.js API (user JWT + service role)            Supabase
  │ POST /calls/{id}/recordings  │                                                │
  │ {filename,mimeType,size,     │ 1 zod validate; role ≥ editor; call in ws      │
  │  consentAttested:true}       │ 2 ext/MIME allow-list, size ≤ limit            │
  │─────────────────────────────▶│ 3 quota: sum(size) of non-deleted + size ≤ quota│
  │                              │ 4 insert row (pending_upload, server path) ───▶│ Postgres (RLS)
  │                              │ 5 createSignedUploadUrl(path) [service role] ──▶│ Storage
  │◀── {recording, upload:{signedUrl, token, path, contentType, expiresAt}} ───────│
  │ PUT file via uploadToSignedUrl(path, token, file, {contentType}) ──────────────▶│ Storage
  │  (progress shown; bucket enforces size + MIME)                                 │
  │ POST /recordings/{id}/complete│                                                │
  │─────────────────────────────▶│ 6 object exists? size == declared? ───────────▶│ Storage (service role)
  │                              │ 7 read first 64 bytes (Range) → magic bytes     │
  │                              │ 8 ok → status=uploaded, uploaded_at, delete_after│
  │                              │   fail → status=failed + enqueue object purge   │
  │◀── {recording} ──────────────│ 9 activity event "recording.uploaded"           │
```

Details:

- **Consent attestation** is required (`consentAttested: true`); stored as
  `consent_attested_at`. The UI shows: "I confirm I had the right to record this call and
  to store this recording."
- **Signed upload URLs** are single-path; Supabase fixes their validity at 2 hours. The
  token is returned once, never logged, and only for the creator.
- **Idempotency:** `POST .../recordings` accepts an `Idempotency-Key` header; repeated keys
  within 24 h return the same pending row and a fresh upload token.
- **Duration:** the client reports `durationSeconds` from audio metadata after upload via
  `PATCH /recordings/{id}` (validated 0–86,400). It is informational only, not trusted for
  billing or security.
- **Retry:** if the PUT fails, the client calls `POST /recordings/{id}/upload-url` for a new
  token (same row/path) while status is `pending_upload`.
- **Replace** (UI action) = upload a new recording, then delete the old one after the new
  one reaches `uploaded`. No in-place overwrite (avoids cache/TOCTOU issues).
- **Resumable uploads (P2):** for unreliable networks, switch to TUS resumable uploads
  (`/storage/v1/upload/resumable`) with a narrowly scoped storage `INSERT` policy that
  requires a matching `pending_upload` row owned by the caller. Not in MVP.

## 4. Playback workflow

1. The player requests `GET /api/v1/workspaces/{ws}/recordings/{id}/playback-url`.
2. The API checks role ≥ editor (see SECURITY_MODEL §4) and `status = 'uploaded'`.
3. The service-role client calls `createSignedUrl(path, 300)` (5 minutes).
4. Response: `{ url, expiresAt }` with `Cache-Control: no-store`.
5. The `<audio>` element uses the URL (`preload="metadata"`); Storage serves HTTP Range
   requests, so seeking works without downloading the whole file.
6. On a media `error` after expiry, or when resuming after more than 4 minutes, the
   player requests a fresh URL and restores `currentTime`.

Rules:

- Signed URLs are **never** stored in the database, client storage, activity metadata,
  logs or error reports.
- No "download" button in MVP; an explicit download (signed URL with `download` filename)
  may be added later with the same authorization.
- Commenters/viewers see metadata and a "Restricted — ask the workspace owner" state.

## 5. Deletion workflow

| Trigger | Behavior |
| --- | --- |
| User deletes a recording (`DELETE /recordings/{id}`) | Owner, or editor who uploaded it. Row → `status='deleted'`, `deleted_at=now()`; path enqueued (`user_delete`); hidden from all queries immediately |
| Call / opportunity / workspace deleted | FK cascade deletes rows; `BEFORE DELETE` trigger enqueues every path (`cascade`) |
| Retention deadline passes | Retention job marks `deleted` and enqueues (`retention`) |
| Upload not completed within 24 h | Abandoned-upload job deletes row and enqueues path (`abandoned`) |
| Verification fails | Enqueued (`failed_validation`) |
| Account deletion | All recordings of owned workspaces enqueued (`account_deletion`) |

**Purge job** (`/api/internal/jobs/purge-storage`, every 5 minutes): takes up to 500
pending queue rows (`FOR UPDATE SKIP LOCKED`), removes objects with the service-role
client, sets `completed_at`; on error increments `attempts` and records `last_error`
(exponential backoff; alert when `attempts ≥ 5`). Deleting an already-missing object counts
as success (idempotent).

**Reconciliation job** (daily): lists bucket objects older than 24 h and compares them with
non-deleted `recording_attachments.object_path`; orphans are enqueued (`cascade`) and
counted in a metric. Target: **0 orphans older than 24 h**.

**Service-level objective:** an object is removed from Storage within **15 minutes** of a
user delete (p99), and within **24 hours** for retention and cascades.

## 6. Retention

| Setting | Default | Options |
| --- | --- | --- |
| `workspaces.recording_retention_days` | `null` (keep until deleted) — **pending product decision** | 30, 90, 180, 365 |

- `delete_after = uploaded_at + retention_days` is set when a recording reaches `uploaded`.
- Changing the setting recomputes `delete_after` for existing recordings; shortening it
  shows the number of recordings that will be deleted and requires confirmation.
- The retention job runs hourly and processes recordings where `delete_after <= now()`.
- Tombstone rows (`status='deleted'`) are hard-deleted after 30 days.

## 7. Quotas and limits

| Limit | MVP value | Enforcement |
| --- | --- | --- |
| Max file size | 100 MB | Client check, API check, bucket limit |
| Workspace storage | 2 GiB (`workspaces.storage_quota_bytes`) | API at upload init (sum of non-deleted `size_bytes`) |
| Upload inits | 30/hour/user | Rate limiter |
| Playback URLs | 120/hour/user | Rate limiter |
| Recordings per call | 10 | API |

## 8. Backups and recovery

- Database backups/PITR restore **metadata only**. Supabase Storage objects are not
  versioned; a deleted recording is **unrecoverable by design**. The UI delete
  confirmation must say so.
- After a DB point-in-time restore, run the reconciliation job in "report" mode first:
  restored rows whose objects no longer exist are marked `failed` with
  `failure_reason='object_missing_after_restore'`.

## 9. Abstraction for portability

Server code accesses storage only through an interface in `src/server/recordings/storage.ts`:

```ts
interface RecordingStorage {
  createUploadUrl(path: string): Promise<{ signedUrl: string; token: string; expiresAt: string }>;
  stat(path: string): Promise<{ sizeBytes: number; contentType: string } | null>;
  readHead(path: string, bytes: number): Promise<Uint8Array>;
  createPlaybackUrl(path: string, ttlSeconds: number): Promise<{ url: string; expiresAt: string }>;
  remove(paths: string[]): Promise<{ failed: { path: string; error: string }[] }>;
  list(prefix: string, olderThan: Date): AsyncIterable<string>;
}
```

The Supabase implementation is the only one in MVP; an S3 implementation could replace it
without touching API contracts.

## 10. Frontend changes required

- Consent checkbox before upload; disabled upload button until checked.
- Upload progress bar, `pending_upload` / `failed` / `uploaded` / restricted states.
- Replace the in-memory `localFileRegistry` with: local object URL preview during upload
  only, then signed playback URLs from the API.
- Player refreshes expired URLs transparently (§4.6).
- Delete confirmation states that deletion is permanent.
- Remove "local preview only — not uploaded" copy once uploads are live.
